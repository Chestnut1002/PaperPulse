# F9 跨源论文合并

同一篇论文会因为命中不同数据源而在库里存成两行。接入 arXiv 之后,这种情况在**同一次搜索里**
就可能撞上,所以从"待办"升级成"必须处理"。

## 1. 背景

论文的唯一约束是 `(来源, 外部 ID)`。这在单源时够用,但检索现在并发查三个源
(Semantic Scholar / arXiv / Crossref),同一篇论文在不同源下的身份完全不同:

```
arXiv    : 2502.19271                                     Contrastive Learning for Rec…
Crossref : 10.1145/3640457.3688186                        Contrastive Learning for Rec…
```

DOI 也救不了:arXiv 预印本的 DOI(`10.48550/arxiv.*`)与正式发表版的期刊 DOI **本就是两个**,
而且实测只有约一成论文登记了正式发表 DOI。

## 2. 目标

1. 跨源的同一篇论文在库里只留一行,收藏 / 评分 / 阅读历史不再分裂
2. 合并**可逆** —— 万一合错,能拆回来
3. 合并**不回退** —— 合并后再遇到被合并掉的那个身份,仍要命中同一行,不能又建一行
4. 不引入模糊匹配带来的静默数据损坏

## 3. 实测依据

在实现之前先量了一次(脚本:`scratch/duplicate_probe.py`,方法:取 arXiv 论文逐篇拿标题去 Crossref 反查):

| 结果 | 篇数 |
| ---- | ---- |
| 标题完全相同 | 21 |
| 标题高度相似(≥0.85) | 4 |
| 差异明显(其实是别的论文) | 7 |
| 查不到正式版 | 28 |

**标题完全相同的那 21 篇里:作者也对得上 20 篇,对不上 1 篇。**

这说明两件事:

- **加作者这一条是有用的**:只看标题,21 次里会合错 1 次;加上作者刚好挡住
- 漏网的主要是括号后缀(`IGNiteR: … (Extended Version)` 对 `IGNiteR: …`),
  以及 Crossref 标题里的 HTML 标签(`<i>SiReN</i>: …`)—— 后者代码里已有清理

> 样本是 60 篇,数量不大,结论是**指示性**的而非定论。规则按保守取。

## 4. 系统设计

### 4.1 匹配规则

一条记录若没能在前两级命中,才走这里。三个条件**全部满足**才算同一篇:

| 条件 | 做法 | 理由 |
| ---- | ---- | ---- |
| **标题相同** | 归一化后逐字符比较 | 见下方归一化细则 |
| **作者相同** | 取**姓氏**、排序后比较 | 正式版常补作者、调顺序、名字缩写形式也变;比全名会漏一大片 |
| **年份相近** | 两边都有年份且相差 ≤ 3 年 | 挡住"同一作者不同时期写了同名论文"。任一方年份缺失则**不合并** —— 宁可多一行,不可合错 |

**标题归一化细则**(按顺序,**这两步的顺序有讲究**):

1. **先**还原 HTML 转义(`&amp;` → `&`)
2. **后**去掉 HTML 标签(`<i>`, `<sub>` …)—— Crossref 的标题里有
3. 去掉括号后缀:`(Extended Version)`、`(Preprint)`、`[v2]` 这类
4. 只保留字母数字,统一小写,压缩空白

> ⚠️ 1 与 2 **不能对调**。反过来先剥标签的话,像 `&lt;i&gt;` 这种**被转义过的标签**
> 会被当成正文留下来,归一化后的标题就跟另一源的同一篇对不上 ——
> 而这种漏合是**静默的**,只在数据里表现为"同一篇存了两行"。实现见 `PaperMatcher.titleKey`。

**作者比较细则**:先还原转义、去首尾空白,再取姓氏 ——

- 含逗号:取**逗号前**那段(`Li, Wei` → `li`)
- 不含逗号且只有一个词:整段保留(中文姓名、单名,不做猜测)
- 不含逗号但有多个词:取**最后一段**(`Wei Li` → `li`)

姓氏各自归一化后参与比较(`PaperMatcher.surnameOf`)。

> 注:中西文姓名格式不统一(中文姓名姓氏在前)是个已知的粗糙处。当前用**集合比较**
> 降低顺序影响;它会让匹配略偏保守(该合的没合),不会造成错误合并。

### 4.2 别名表:合并要记得住,也要能反悔

**如果只"更新已有行、不新建",合并是留不住的** —— 下次再遇到被合并掉的那个身份,
按 `(来源, 外部 ID)` 查 paper 表查不到,又会新建一行。

所以新增一张表,记录"这个身份其实指向那一行":

```
paper_alias
  id          BIGINT PK
  paper_id    BIGINT       -- 指向被采用的那一行
  source      VARCHAR(32)
  external_id VARCHAR(128)
  created_at  DATETIME
  UNIQUE (source, external_id)
```

唯一约束保证一个身份至多指向一行。

它同时是**后悔药**:合错了,删掉这条别名,下次遇到那个身份就会重新建行,数据自己长回来。

与既有约定一致:**不加外键**(F6 起就没有外键,理由记录在当年的日志里)。

### 4.3 解析顺序

`PaperService.resolve` 的查找顺序从两级扩到四级:

```
① 按 DOI 查                    —— 最强的跨源信号(两个源引用同一条已发表记录时)
② 按 (来源, 外部 ID) 查 paper   —— 同一身份重复提交,原有行为不变
③ 按 (来源, 外部 ID) 查 alias   —— 这个身份之前被合并过,指向那一行
④ 按"标题 + 作者 + 年份"查       —— 命中就采用,并把本次身份记成别名
⑤ 都没有 → 新建
```

前两级是现有行为,不动;③④ 是本功能新增。

**并发**:④ 的两步(查、记别名)与建行都在既有的 `REQUIRES_NEW` 写事务里;
别名表的唯一约束冲突也走现有的"插入失败后重查"恢复路径。

### 4.4 合并时如何更新元数据

现有 `applyMetadata` 是"新值非空且与旧值不同就覆盖"。**这个语义在合并路径上不合适**:
预印本的标题带"(Extended Version)"、作者列表可能更多,直接覆盖会让标题在两次检索之间来回翻。

所以合并路径用**只补空缺、不覆盖已有值**的语义:
被合并方只贡献自己有的、而目标行没有的字段(常见的正是反过来:正式版补上会议名,预印本补上摘要)。

> 不引入"哪个来源更权威"的判断 —— 那种规则说不清,而且各领域不同。

## 5. 模块划分

| 文件 | 职责 |
| ---- | ---- |
| `paper/PaperAlias.java` + `PaperAliasRepository.java` | 别名表 |
| `paper/PaperMatcher.java` | **纯逻辑**:标题归一化、作者键、年份判定。不碰数据库,可单测 |
| `paper/Paper.java` | 加 `title_key`(归一化标题)列 + 索引,供 ④ 查询 |
| `paper/PaperService.java` | 解析顺序扩到四级;合并路径的元数据语义 |
| 测试 | `PaperMatcherTest`(纯逻辑)+ `PaperMergeApiIntegrationTest`(端到端) |

`title_key` 存在的理由:④ 要按标题查,而标题字段本身是原始文本,直接 LIKE 既慢又不准。
归一化后的值单独存一列并加索引。

## 6. 核心流程

```
一次检索返回一篇 arXiv 论文
   ↓
① 有 DOI? → 查不到
② (arxiv, 2502.19271)? → 查不到
③ 别名里有 (arxiv, 2502.19271)? → 没有
④ 用 title_key + 作者 + 年份查 → **命中** Crossref 那一行
   ↓
采用该行;录入别名 (arxiv, 2502.19271) → 那一行
补齐该行缺失的字段(不覆盖已有值)
   ↓
下次同样的检索再来 → ③ 直接命中,不再走 ④,也不再新建
```

## 7. 技术选型原因

- **为什么不做纯展示层归组**:收藏 / 评分 / 阅读历史引用的是本地 id,库里两行就意味着数据分裂。
  只在展示时合并等于把问题藏起来。
- **为什么不按标题模糊匹配(编辑距离)**:模糊阈值说不出道理,而且实测里"标题差异明显"的那批
  大多是**不同的论文**(作者也不同)。用可解释的三条件,规则能讲清楚,错了也知道为什么错。
- **为什么别名要独立成表而不是加个字段**:一篇论文可能被合并多个身份
  (预印本 + 会议版 + 期刊版),一个字段放不下;而唯一约束天然表达"身份 → 行"的映射。

## 8. 未来扩展

- **合并的审计**:目前只记 `created_at`。若将来要人工复核,可加 `matched_by`(命中哪条规则)。
- **撤销入口**:别名表已经让撤销在数据上可行,将来可以给个管理接口。
- **OpenAlex 接入**:它的 DOI 齐全,会让 ① 的命中率明显提高,④ 用得更少 —— 规则越靠前越可靠。
