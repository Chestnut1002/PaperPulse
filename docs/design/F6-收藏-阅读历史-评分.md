# F6 收藏 / 阅读历史 / 论文评分 设计文档

> 所属需求:REQ-001(用户系统),功能点 F6 —— **REQ-001 的最后一个功能点**
> 状态:✅ 已完成(2026-09-16)
> 前置:F1–F5

---

## 1. 背景

F1–F5 建起的是"用户是谁"和"用户想要什么"。F6 处理的是**用户做了什么**。

这三个动作在推荐系统里的地位与前两者不同:兴趣标签是用户**自己声明的**偏好(显式、稀疏、
可能失真),收藏/阅读/评分是**行为留下的痕迹**(隐式为主、随使用自然增长)。REQ-004 的推荐模型
主要靠后者,前者只在冷启动阶段顶上。

所以 F6 的产出不只是三张表,而是**推荐系统的行为数据底座**。

## 2. 目标

| 编号 | 目标 | 达成情况 |
| ---- | ---- | ---- |
| G1 | 论文元数据在本地有且只有一份 | `paper` 表,`(来源, 外部 ID)` 唯一 |
| G2 | 收藏、阅读历史、评分三类行为可记录、可查询、可撤销 | 10 个接口 |
| G3 | 论文在多个用户之间共享,行为各自独立 | `paper` 与三张行为表分离 |
| G4 | 读路径不产生 N+1 查询 | 列表接口批量取论文 |
| G5 | 有自动化回归覆盖 | 25 条集成测试 |

**非目标**:

- 不做论文检索 —— 属于 REQ-002。F6 只负责"已经有了的论文怎么记"
- 不做推荐算法 —— 属于 REQ-004
- 不做分页游标 —— 历史有上限,收藏和评分的量级不足以成为问题

## 3. 系统设计

### 3.1 数据模型

```
                 ┌──────────────────────┐
                 │        paper         │  公共语料,不属于任何用户
                 │  (source,ext_id) 唯一 │
                 └───────────┬──────────┘
                             │ 被引用
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
┌───────────────┐   ┌──────────────────┐   ┌──────────────┐
│ paper_favorite│   │paper_read_history│   │ paper_rating │
│ (user,paper)  │   │   (user,paper)   │   │(user,paper)  │
│     唯一       │   │       唯一        │   │     唯一      │
│   = 状态       │   │    = 计数 + 时间   │   │   = 状态      │
└───────────────┘   └──────────────────┘   └──────────────┘
```

三张行为表**互不引用**。一个用户可以对同一篇论文只收藏不打分、只读不收藏,
或者任何组合。

### 3.2 为什么论文元数据要落本地库

只存外部 ID 的方案看起来更"轻",但有两个它解决不了的问题:

**一、外部服务不可用时收藏夹打不开。** Semantic Scholar 的 429 在本项目里是**实测会发生的**
(F5 期间观测到)。一个"我的收藏"页面每次渲染都要回源二十次,只要 S2 抽风就整页白屏。
自己的数据依赖别人的可用性,是不该有的耦合。

**二、REQ-006 的离线评测需要本地语料。** 评测要反复扫全量交互、按论文算指标,
每次都回源既慢又不可复现 —— 外部数据是**会变的**,同一份实验跑两次结果不同就没有意义了。

**代价**是元数据可能过时。接受的依据:论文的标题、作者、年份几乎不变;
会变的只有引用数这类指标,而它们不参与本项目当前的推荐逻辑。

### 3.3 论文去重靠 `(source, external_id)`

**为什么不能只用 externalId:** 不同来源各有自己的 ID 空间,撞号不代表同一篇。

**为什么一篇论文只有一行:** 多用户收藏同一篇论文时,如果各存一份,
推荐系统里的"共现"统计会把同一篇论文当成多篇,星标数也会翻倍。
唯一约束把这个不变量交给数据库保证,而不是指望服务层每次都记得去重。

### 3.4 状态 vs 事件 —— 本次最重要的一个区分

| | 收藏 | 评分 | 阅读 |
| --- | --- | --- | --- |
| 语义 | 状态 | 状态 | 可重复的行为 |
| 一人一篇 | 一行 | 一行 | 一行 |
| 重复操作 | 幂等,返回已有的 | 覆盖分数 | **计数加一**,时间前移 |

写反了**不会报错**,只会慢慢攒出脏数据:把收藏当事件记,用户取消再收藏就会有两条"收藏"
记录;把阅读当状态记,读十次只算一次。所以三者用了不同的写法,并且都有对应用例盯着
(F6-2/F6-9 管幂等,F6-15 管计数,F6-20 管覆盖)。

### 3.5 幂等的边界在哪里

同样是"重复操作",两个接口的响应刻意不同:

| 操作 | 结果 |
| ---- | ---- |
| 重复收藏已收藏的论文 | **200 成功** |
| 清空本来就没有记录的阅读历史 | **204 成功** |
| 取消一个没收藏过的论文 | **404** |
| 取消一个没打过分数的论文 | **404** |

分界线是**结果状态是否与意图一致**:

- 重复收藏 → 意图是"让它处于已收藏状态",它已经处于了 → 成功
- 清空空历史 → 意图是"让它为空",它已经空了 → 成功
- 取消没收藏过的 → 意图是"让它从未收藏变为不存在",但**根本没有这回事** → 404

最后一条不是吹毛求疵:前端拿着一个过期的界面点删除,回 200 会让它以为删掉了,
用户下次刷新发现又冒出来,却不知道是哪一步出的问题。**明确的失败优于善意的猜测**。

### 3.6 元数据只增不减

`applyMetadata` **只覆盖非空字段**。同一个来源在不同时刻返回的字段完整度不一样
(搜索接口常常只给标题和 ID,详情接口才有摘要)。如果无条件覆盖,
一次信息不全的提交就会把已经存好的摘要抹成空。

这是**静默错误** —— 它不违反任何约束、不报任何错,只是数据慢慢变少。
所以专门有一条用例(F6-6)盯着:提交一次完整元数据,再提交一次缺字段的,断言摘要还在。

### 3.7 并发首次提交同一篇论文

这是 F6 里唯一一处"写错会直接报 500"的地方,也是唯一做了冲突恢复的地方。

```
请求 A: SELECT → 没有 → INSERT ✓
请求 B: SELECT → 没有 → INSERT ✗ Duplicate entry
```

**数据源不在事务里** —— 论文本来就来自外部检索,多个用户同时收藏同一篇热门论文
是完全正常的使用场景,不是异常。

处理方式:插入放在**独立的 `REQUIRES_NEW` 事务**里,失败就重查一次。
两个细节缺一不可:

1. **必须是独立事务。** 如果建行和重查在同一个事务里,Hibernate 的会话在刷盘失败后
   已经不可用,紧接着的查询会跟着失败 —— 想恢复也恢复不了。
2. **不能用 `@Transactional` 注解。** 私有方法上的注解不生效,同类自调用也绕过代理,
   而且**不会有任何报错**,注解形同虚设。这里用 `TransactionTemplate` 显式划定边界,
   没有这个陷阱。

**实测证据**(不是推理):八个线程用 `CyclicBarrier` 同时提交同一篇新论文,
其中**七个**撞上了唯一约束。把恢复代码换成直接重抛后,只有 F6-25 这一条用例失败,
报 `ExecutionException: Duplicate entry`。证据同时记在 `PaperService#resolve` 的注释里。

作为对照,**阅读次数**的并发没有处理:它是"读出来 +1 再写回",并发时会丢一次计数。
这是**刻意接受**的 —— 阅读次数是弱信号,少算一次不影响推荐质量;
而它的严重程度(用户看不到错误)与论文冲突(用户看到 500)完全不同。
两者的处理方式不同,是有意的,不是遗漏。

### 3.8 三组接口互相独立

收藏列表**不会**带上评分。前端同时需要两者时取两个接口,在客户端按 `paperId` 合并。

这样做的好处:每个接口的返回形状保持单一,不需要为"N 个可选关联字段"设计三套变体;
后端的查询也不会因为将来多一个关联而变成多路 join。

### 3.9 路径里不出现用户 id

所有接口都挂在 `/api/users/me` 下,当前用户一律取自 token。

如果写成 `/api/users/{userId}/favorites`,就得在每个方法里校验"路径上的 id 是不是你自己" ——
一旦哪一处漏掉,就是一个越权漏洞。**让这种错误不可能写出来,比写对更重要。**

## 4. 模块划分

```
com.paperpulse.paper                   论文语料 —— 与用户无关
├── Paper.java                         实体
├── PaperSource.java                   来源枚举(S2 / arXiv / Crossref)
├── StringListConverter.java           作者列表 ⇄ JSON 文本列
├── PaperRepository.java
├── PaperService.java                  幂等 upsert + 并发冲突恢复
├── PaperController.java               POST /api/papers
└── dto/PaperInput.java, PaperResponse.java

com.paperpulse.library                 用户 × 论文 —— 行为数据
├── PaperFavorite.java / Repository    收藏(状态)
├── PaperReadHistory.java / Repository 阅读(计数)
├── PaperRating.java / Repository      评分(状态)
├── LibraryService.java
├── LibraryController.java
└── dto/ FavoriteResponse, HistoryResponse, RatingResponse, RatingRequest
```

**分成两个包而不是一个**:`Paper` 不属于任何用户,REQ-002 检索回来之后也会用到它;
行为数据则以用户为主体。两者的生命周期不同 —— 论文表可以一直长,
行为数据是用户私有且随用户走的。

## 5. 数据流

### 写路径

```
① 前端拿到一篇论文(现在来自测试数据,REQ-002 完成后来自检索)
   POST /api/papers  { source, externalId, title, authors, ... }
        └─► resolve(): 校验来源 → 独立事务里"查到就更新、查不到就建"
        └─► 返回 { id, ... }        ← 这个 id 是后面所有操作的凭据

② 记行为,全部用上面拿到的本地 id
   POST   /api/users/me/favorites/{paperId}
   POST   /api/users/me/history/{paperId}
   PUT    /api/users/me/ratings/{paperId}  { "score": 5 }
```

### 读路径

```
GET /api/users/me/favorites
  → findByUserIdOrderByFavoritedAtDesc   一次查询拿到行为行
  → paperService.byIds(...)              一次查询拿到全部论文   ← 避免 N+1
  → 组装成内嵌论文的响应
```

论文 id 在库里查不到时**过滤掉而不是报错**:某条行为记录指向的论文没了,
不该让整个列表打不开。

## 6. 接口

| 方法 | 路径 | 说明 | 返回 |
| ---- | ---- | ---- | ---- |
| POST | `/api/papers` | 提交论文元数据(幂等 upsert) | 200 `PaperResponse` |
| GET | `/api/users/me/favorites` | 收藏列表,最近在前 | 200 |
| POST | `/api/users/me/favorites/{paperId}` | 收藏(幂等) | 200 |
| DELETE | `/api/users/me/favorites/{paperId}` | 取消收藏 | 204 / 404 |
| GET | `/api/users/me/history?limit=` | 阅读历史,最近在前 | 200 |
| POST | `/api/users/me/history/{paperId}` | 记一次阅读(次数累加) | 200 |
| DELETE | `/api/users/me/history` | 清空历史(幂等) | 204 |
| GET | `/api/users/me/ratings` | 评分列表 | 200 |
| PUT | `/api/users/me/ratings/{paperId}` | 打分 / 改分(覆盖) | 200 |
| DELETE | `/api/users/me/ratings/{paperId}` | 取消评分 | 204 / 404 |

`limit` 默认 100,上限 500。

### 数据表

```sql
CREATE TABLE paper (
    id                  BIGINT AUTO_INCREMENT PRIMARY KEY,
    source              VARCHAR(32)  NOT NULL,   -- 存枚举名,不存序号
    external_id         VARCHAR(128) NOT NULL,
    title               VARCHAR(512) NOT NULL,
    authors             TEXT,                    -- JSON 数组
    abstract_text       TEXT,
    publication_year    INT,
    venue               VARCHAR(256),
    url                 VARCHAR(512),
    metadata_updated_at DATETIME(6)  NOT NULL,
    CONSTRAINT uk_paper_source_external_id UNIQUE (source, external_id)
);

CREATE TABLE paper_favorite (
    id           BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id      BIGINT      NOT NULL,
    paper_id     BIGINT      NOT NULL,
    favorited_at DATETIME(6) NOT NULL,
    CONSTRAINT uk_paper_favorite_user_paper UNIQUE (user_id, paper_id)
);

CREATE TABLE paper_read_history (
    id           BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id      BIGINT      NOT NULL,
    paper_id     BIGINT      NOT NULL,
    last_read_at DATETIME(6) NOT NULL,
    read_count   INT         NOT NULL,
    CONSTRAINT uk_paper_read_user_paper UNIQUE (user_id, paper_id)
);

CREATE TABLE paper_rating (
    id       BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id  BIGINT      NOT NULL,
    paper_id BIGINT      NOT NULL,
    score    INT         NOT NULL,
    rated_at DATETIME(6) NOT NULL,
    CONSTRAINT uk_paper_rating_user_paper UNIQUE (user_id, paper_id)
);
```

## 7. 技术选型原因汇总

| 决策 | 选择 | 主要理由 |
| ---- | ---- | ---- |
| 元数据存放 | 落本地库 | S2 会 429;离线评测需要可复现的本地语料 |
| 论文唯一标识 | `(source, external_id)` | 不同来源的 ID 空间会撞号 |
| 行为表划分 | 三张独立表 | 三类信号的语义与生命周期不同 |
| 阅读历史表示 | 计数 + 时间,非事件流水 | 推荐要的就是这两个数,流水每次都要 GROUP BY |
| 作者列表存储 | JSON 文本列 | 逗号拼接会毁掉「姓, 名」写法的作者名 |
| 论文冲突恢复 | `REQUIRES_NEW` + 重查 | 同一事务内刷盘失败后会话不可用,无法重查 |
| 事务划定方式 | `TransactionTemplate` | 自调用会绕过 `@Transactional` 代理且不报错 |
| 列表取论文 | 批量 `findAllById` | 避免 N+1 |
| 当前用户来源 | token,不出现于路径 | 让越权写不出来 |
| 评分刻度 | 1–5 整数 | 与 F5 兴趣权重同一套刻度 |

## 8. 测试

25 条集成测试(`LibraryApiIntegrationTest`):

| 分组 | 用例 | 针对的风险 |
| ---- | ---- | ---- |
| 论文落库 | F6-1 ~ F6-7 | 去重、跨来源撞号、元数据只增不减、必填校验 |
| 收藏 | F6-8 ~ F6-13 | 幂等、404 边界、时间倒序 |
| 阅读历史 | F6-14 ~ F6-18 | 次数累加而非追加、重读顶到最前、limit |
| 评分 | F6-19 ~ F6-22 | 覆盖而非追加、越界、缺字段 |
| 鉴权与隔离 | F6-23 ~ F6-24 | 10 个接口全部 401、用户间互不影响 |
| **并发** | **F6-25** | **首次提交同一篇论文的冲突恢复** |

**反向验证**(F5 的做法):把 `applyMetadata` 改成无条件覆盖后重跑,只有 F6-6 失败;
把并发恢复换成直接重抛后重跑,只有 F6-25 失败。两次都精确命中了目标用例,
说明它们不是"陪跑"的。

## 9. 未来扩展

| 方向 | 说明 |
| ---- | ---- |
| 论文改由后端写入 | REQ-002 落地后,论文应由后端从 S2 拉取后写入,`POST /api/papers` 收窄为只读,消除"客户端可抢占 externalId"的问题 |
| `paper_author` 关联表 | 现在作者是 JSON 文本,不支持按作者查询。REQ-004 要做"同作者"特征时需要真正的关联表 |
| 阅读事件流水 | 现在只存计数。要做会话级分析(如"连续读了三篇同一主题")需要事件表 |
| 分页 | 收藏和评分的量级目前不值得做;真需要时上游标而不是 offset |
| 负反馈 | 目前没有"不感兴趣"。收藏/评分的反面是"不操作",信号太弱,需要一个显式通道 |
| 论文删除 | 现在只增不删。真要下线论文时,需要注意三张行为表里的孤儿引用(读路径已能容忍) |
