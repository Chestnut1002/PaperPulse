# F12 精读问答

REQ-003 阶段 1:**单篇论文的多轮问答,回答带引用**。

## 1. 背景

到此为止这个助手能帮你**找到**论文,但不能帮你**读**论文。检索、推荐都有了,精读是三条腿里唯一没建的一条。

需求原文写的是「锚点+动态截断 **/** RAG」—— 那是两种做法,对应两种场景:

| 场景 | 做法 |
| ---- | ---- |
| **单篇论文多轮问答** | 全文常驻上下文,轮次接近上限时截断到最近几轮(**锚点**) |
| 跨论文检索问答 | RAG(向量检索 + 引用片段) |

这也正是 PaperAgent 的做法(它的三大借鉴设计之一):**全文常驻,RAG 留给跨论文场景**。

## 2. 目标

1. 能对一篇论文连续提问,回答**基于原文**而不是模型的记忆
2. 每条回答**说得出依据来自哪一节**
3. 遵守上下文上限:**接近上限时截断旧轮次,而不是报错**
4. 探测先行:全文能不能拿到、拿到的结构能不能用,先验证再设计

**不在本次范围**:跨论文 RAG、会话持久化、非 arXiv 论文的 PDF 解析。

## 3. 系统设计

### 3.1 全文从哪来

**arXiv 的 HTML 版**(`https://arxiv.org/html/{arxivId}`)。实测:

| 项 | 实测值 |
| ---- | ---- |
| 可达性 | HTTP 200,1.3 秒 |
| 体积 | HTML 438KB,纯文本约 154KB |
| 结构 | 33 个 `<section>`,能按节切开 |
| 覆盖 | 2025 年、2023 年、**连 2017 年的老论文都有**(arXiv 回填过) |

**只有 arXiv 来源的论文能精读。** Crossref 的期刊论文没有可抓的开放全文 —— 这是明确的边界,不是遗漏。

**顺带扩大覆盖**:Semantic Scholar 的记录里带 arXiv ID(`externalIds.ArXiv`)。把它存进 `paper` 表,一部分 S2 论文也能精读。所以 `paper` 加一列 `arxiv_id`。

### 3.2 取全文与切节

用 BeautifulSoup 把 HTML 拆成**有序的节**:每节带标题与正文,丢掉导航、页脚、脚本。

**数学公式是个已知问题**:arXiv 的 HTML 用 MathML,转成纯文本会变成一堆碎片。

> **已修复(2026-10-01,P1b)**:不再原样保留。`fulltext.py` 取每个 `<math>` 上的
> `application/x-tex` 注解 —— 那正是**公式的 LaTeX 源码**,本来就是原始形态。
> 当初判断"要引入 MathML 渲染"是找错了方向:源码就藏在 HTML 里,不需要渲染。
>
> 而且实际后果比"质量打折"严重:通用文本抽取会把**渲染出的符号和 LaTeX 源码两份都拿到**、
> 粘在一起,抽出来是 `v ∈ V v\in V` 这种乱码。实测四篇论文共 1569 个公式**一个不缺**都带源码,
> 所以这不是碰运气,是 arXiv HTML 的固定特性。

**参考文献与附录在送进上下文前截掉**:它们对"这篇论文讲了什么"帮助很小,却可能占掉三分之一篇幅。

### 3.3 引用怎么产生

**不让模型自己编引用文本。** 做法是:

1. 送进上下文时,每一节带上编号标记(如 `[[§3]] 方法`)
2. 要求模型在回答里用这些标记
3. 模型另外返回**它用了哪几节的编号**
4. **后端按编号去原文取该节的开头一段作为依据片段** —— 逐字来自原文,不经过模型

这样引用是**构造上可信**的:模型只负责"指哪一节",不负责"抄哪句话"。

### 3.4 上下文与截断

```
送入 = 全文(截掉参考文献后) + 最近 N 轮对话 + 本轮提问
```

**接近上限时从最旧的轮次开始丢**,直到落进预算。丢的时候**不静默**:
回答里带上"已省略前面 N 轮"的说明 —— 用户该知道自己问了什么被丢了。

**预算可配**(`QA_CONTEXT_BUDGET`),默认取保守值。Token 数**按字符估算** ——
我们没有 DeepSeek 的分词器,只能按经验比例估,所以要保守,并在注释里写明这是估算。

### 3.5 会话历史放前端

前端持有对话历史,每轮把**最近若干轮**随请求带上;ai-service **不维持会话状态**。

好处:服务无状态,重启不丢对话;而且"截断"发生在发送之前,规则看得见。
代价:每轮会把最近几轮重发一遍(相对全文的体积可以忽略)。

## 5. 数据流

```
用户在论文问答页提问
   ↓  { paperId, question, history: [最近 N 轮] }
Java ReadingService
   ├─ 取论文,确认它有 arxivId(没有就明确告知"这篇没有可精读的全文")
   ↓  { arxivId, question, history }
Python POST /qa
   ├─ 取全文(本地文件缓存,首次联网抓;重启不丢)
   ├─ 切节 → 编号 → 拼上下文
   ├─ 截断:超预算就丢最旧轮次
   ├─ 调 DeepSeek,要求用 [[§n]] 标记并返回用到的节号
   └─ 按节号从原文取依据片段
   ↓  { answer, citations: [{sectionIndex, title, excerpt}], omittedTurns }
前端渲染回答与依据
```

## 6. 核心流程

| 情况 | 处理 |
| ---- | ---- |
| 论文没有 arXiv ID | 明确告知"这篇没有可精读的全文",**不报 500** |
| 抓不到 HTML(网络/该篇没有) | 说清是哪一篇拿不到,让用户能判断是网络还是这篇不支持 |
| 模型没有返回节号 | 回答照常返回,但不带依据 —— **不编造引用** |
| 模型给的节号不存在 | 丢掉那一条,不猜 |
| 上下文超预算 | 从最旧轮次开始丢,并在回答里注明丢了 N 轮 |

## 7. 技术选型原因

| 选择 | 理由 |
| ---- | ---- |
| **锚点+截断而不是 RAG** | 一篇论文 154KB(≈4 万 token)装得下。RAG 要引入向量库与切块策略,而单论文场景里"全文都在"比"检索得准"更可靠 |
| **arXiv HTML 而不是 PDF** | 实测可达且**带结构**(33 个 section),不必写 PDF 解析;PDF 那条路要引 PyMuPDF 之类的重依赖 |
| **引用由后端从原文取** | 模型只负责"指哪一节"。让它抄原文,它就会**编**原文 —— 而引用编造比回答出错更糟,因为它看起来像证据 |
| **会话放前端** | 服务无状态、重启不丢对话;截断规则也变得可见 |
| **先探测再设计** | 全文能不能拿、有没有结构、老论文覆不覆盖 —— 这三条都是实测出来的,不是假设 |
