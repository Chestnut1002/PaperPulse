# F13 标题反查 arXiv 编号

REQ-003 阶段 3:**没有 arXiv 编号的论文,拿标题去 arXiv 找预印本** —— 把"能精读"的比例从 40~45% 提上去。

## 1. 背景

精读的全文只从 **arXiv 的 HTML 版**取,所以 `paper.arxiv_id` 决定一篇论文能不能精读。
而实测(`scratch/arxiv_html_coverage.py`,2026-09-30)显示检索结果里**只有约一半带这个编号**:

| 来源 | 带 arXiv 编号 |
| ---- | ---- |
| arXiv | 11/11(它自己就是) |
| Semantic Scholar | 4/8(索引里的 `externalIds.ArXiv`) |
| **Crossref** | **0/11**(它的 DOI 是期刊 DOI,反推不出编号) |

综合下来**约 40~45% 的检索结果能精读**。主功能是"帮助用户精读论文",这就是它当前最大的缺口 ——
也是 P3 优先于跨论文 RAG(P2)的原因。

## 2. 目标

1. 对没有 `arxiv_id` 的论文,按**标题**去 arXiv 找预印本;找到就把编号补进 `paper.arxiv_id`
   —— **一次查到,永久生效,所有用户受益**
2. 认不出来时**宁可说没找到,不可认错**:认错会把用户领到**另一篇论文**的全文上
3. 三个列表页对这类论文也给出入口(现在 `v-if="paper.arxivId"` 让它们连入口都没有)

**不在本次范围**:非 arXiv 论文的 PDF 解析(P4)、跨论文 RAG(P2)、用摘要/引用数反查。

## 3. 系统设计

### 3.1 分工:捞在 Python,认在 Java

Python 只负责"把 arXiv 上的候选捞回来";**认不认由 Java 侧的 `PaperMatcher` 决定** ——
跨源合并已经有一套经过 60 篇样本实测的规则(标题归一化 + 作者姓氏 + 年份 ±3 年),
标题反查**复用同一份**,不重写第二套归一化。

### 3.2 查询怎么构造(全部来自实测)

| 实测 | 结论 |
| ---- | ---- |
| `ti:"整句"` 精确短语 | 能找到;但标题措辞差一个内容词就 **0 条** |
| `ti:词1 AND ti:词2 …` | 措辞有出入也能找到 |
| 标题里带 `&`、未闭合引号 | **arXiv 会静默改写成另一个查询**(`ti:a & b` → `ti:a OR all:b`),必须先剔掉语法字符 |
| 标题不存在 | 返回**空 feed**,不是报错 |
| 限流时(`2026-10-01` 连续探测触发) | 返回 **429 且 body 为空**;`_fetch_text` 已有重试,重试仍失败则抛错 → 503 —— **不会把限流误判成"没找到"** |
| 词尾冒号(`ti:LightGCN:`) | 实测**照常命中** —— 不用为它做特殊处理 |

所以:先精确短语;0 条再退化到"显著词 AND"(丢掉停用词,最多 8 个);
两次都空就返回空列表 —— **"没找到"是正常结果,不是异常**。

### 3.5 我们自己没有作者与年份时的退让(2026-10-01 补)

标准匹配要求**作者 + 年份**佐证,而库里有一批记录这两项都是空的 ——
实测库里 166 篇里有 **8 篇**「无编号 + 无作者 + 无年份」,**全部来自 Crossref**。
对它们标准规则永远判否,于是 arXiv 上就算有标题一字不差的预印本也读不了:

| 库里记录 | arXiv 上的候选 | 标准规则 | 现在 |
| ---- | ---- | ---- | ---- |
| `Polymer-Agent: Large Language Model Agent for Polymer Design`(无作者、无年份) | 同名,`2601.16376` | 判否 | **认**(实测已落库) |
| `Large Language Model Agent for Modular Task Execution in Drug Discovery`(同上) | 同名,`2507.02925` | 判否 | **认**(实测已落库) |

于是给反查一条**退让规则**(`PaperMatcher#matchesByTitleAlone`),三个条件同时满足才生效:

1. **我们这边既无作者也无年份** —— 有任何一项佐证就必须走标准规则;
2. 标题归一化后**完全一致**(不是相似);
3. 标题**至少 4 个词** —— 挡掉 `Editorial` 这类通用短标题。

**跨源合并不许用这条规则**:合并错了是把两篇论文并成一篇、收藏评分挂到错处,不可逆;
反查错了只是把用户领到标题相同的另一篇全文上,代价小一个量级。

### 3.3 触发方式:用户手动,不自动

- 等待应当发生在**用户主动操作之后**(既有设计原则)。没编号的论文占一多半,
  进页面就自动查会让大多数访问白等几秒。
- 精读页的"读不了"面板上给一个按钮:**「在 arXiv 上找找看」**。
- 查到后编号写进 `paper` 行,后续访问、其他用户都不再查。

### 3.4 什么落库、什么不落库

| 结果 | 处理 |
| ---- | ---- |
| **找到** | 落库(`paper.arxiv_id`)—— 论文行是共享的,一次查到所有人受益 |
| **没找到** | **不落库**(不做负缓存)—— 负结果会过期(arXiv 在持续回填),正结果不会;代价只是重复点击要再查一次 |

## 4. 模块划分

```
ai-service/
  app/sources.py     search_arxiv_by_title(短语 → 显著词退化;复用 arxiv_to_paper)
  app/schemas.py     ArxivTitleLookupRequest / ArxivTitleLookupResponse(候选列表)
  app/main.py        POST /lookup/arxiv-by-title

backend/.../reading/
  ReadingController  POST /api/papers/{id}/arxiv-lookup
  ReadingService     已有编号直接返回;候选逐个过 PaperMatcher;全不中 404
  AiReadingClient    调 Python 的标题反查

backend/.../paper/
  Paper / PaperService   attachArxivId:只填空缺、幂等、写事务

frontend/
  views/PaperReadingView.vue            「在 arXiv 上找找看」按钮与三种结果
  views/{Search,Library,Recommend}View  无编号时入口文案改为「找可读版本」
  api/reading.js                        resolveArxiv(paperId)
```

## 5. 数据流

```
用户在精读页点「在 arXiv 上找找看」
   ↓ POST /api/papers/{id}/arxiv-lookup
Java ReadingService
   ├─ 已有 arXiv 编号 → 直接返回(不打上游)
   ↓ POST /lookup/arxiv-by-title { title }
Python
   ├─ ti:"标题"(语法字符剔除后)
   ├─ 0 条 → ti:显著词1 AND ti:显著词2 …
   └─ 条目映射成统一论文形状(复用 arxiv_to_paper)
   ↓ { candidates: [...] }(空列表也是正常结果)
Java
   ├─ 逐个过 PaperMatcher(标题 + 作者 + 年份 ±3,三条件全中)
   ├─ 命中 → attachArxivId 落库 → 返回论文(前端问答界面出现)
   └─ 全不中 → 404「arXiv 上没有找到这篇论文的预印本」
```

## 6. 核心流程(边界情况)

| 情况 | 处理 |
| ---- | ---- |
| 论文已有编号 | 直接返回,**不打上游** |
| 我们这边无作者也无年份、标题一致且 ≥4 词 | 认(退让规则,见 §3.5)—— 否则这批永远读不了 |
| 我们这边有作者或年份 | 一律走标准规则,该不认就不认 |
| 候选"像但不是"(标题同、作者不同/年份差太多) | 不认 —— 宁可漏认,不可错认 |
| 候选缺作者或缺年份 | 不认(匹配规则对缺值一律判否) |
| 候选的 `arxivId` 为空 | 跳过(理论上不会有,但不拿空值去落库) |
| arXiv 不可达 | 503,与检索接口同一套语义 |
| 没找到 | 404 + 一句人话;原文链接仍然可点 |
| 并发重复点击 | `attachArxivId` 幂等:只填空缺,不覆盖已有值 |

## 7. 技术选型原因

| 选择 | 理由 |
| ---- | ---- |
| **复用 `PaperMatcher`** | 规则只有一份;它经过实测校准(60 篇样本验证"加作者这一条挡掉了会合错的那次") |
| **匹配放 Java 侧** | Python 只做"捞",不做"认" —— 否则要维护第二套归一化规则,两处迟早不一致 |
| **手动触发** | 等待发生在用户操作之后;自动查会让大多数访问白等 |
| **不做负缓存** | 负结果会过期(arXiv 持续回填老论文的 HTML 版),正结果不会 |
| **查询不按年份过滤** | 预印本与正式版可能差 1~3 年,过滤会误杀;年份交给匹配规则判 |
| **短语失败后退化到显著词 AND** | 实测:措辞差一个词短语就 0 条,而 AND 形式能找到 |
| **退让规则只给反查用** | 两条路的错认代价差一个量级:合并错了不可逆,反查错了只是领错一篇全文 |

## 8. 未来扩展

| 方向 | 说明 |
| ---- | ---- |
| **作者名进查询**(`au:` 字段) | 能提高精确度,但作者表写法差异会降召回 —— 要先实测再定 |
| **摘要/引用数反查** | 标题认不出来时的第二条路 |
| **P4 PDF 解析** | arXiv 上确实没有的论文,这是唯一的出路 |
| **覆盖率作为定期指标** | 反查救回多少,可以用脚本对真实检索结果定期重测 |
| **候选交给用户确认** | 标题只是"相似"而非一致时的第二条路(如缩写、副标题差异);本次两条实测用例标题一字不差,让人确认也看不出差别,故未做 |

## 9. 实测结果(2026-10-01)

跑通后对真实检索结果抽了两批(共 14 篇无编号论文)逐篇反查:

| 结果 | 篇数 | 说明 |
| ---- | ---- | ---- |
| 救回 | 2 | 都是"我们这边无作者无年份"的记录,靠 §3.5 的退让规则 |
| arXiv 上确实没有预印本 | 12 | 逐条外部核实过:如 MIGNN 是 SciTePress 会议论文、GenGCL 是 Neurocomputing 期刊论文 |

**结论:P3 的价值是真实的,但增益受语料构成限制。** 这批无编号论文里大多数是
"只发在期刊/会议上、从来没有预印本"的论文 —— 反查对它们无能为力,只能靠 P4(PDF 解析)。
设计时"50% → 70%+"的估计偏乐观:它假设无编号论文大多有预印本,实测并非如此。
