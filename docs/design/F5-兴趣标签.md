# F5 兴趣标签 设计文档

> 所属需求:REQ-001(用户系统),功能点 F5
> 状态:✅ 已完成(2026-09-16)
> 前置:F1–F4(注册 / 登录 / JWT 鉴权闭环)

---

## 1. 背景

REQ-001 的前四个功能点解决的是"用户是谁"。F5 开始进入"用户想要什么" —— 这是个性化推荐
(REQ-004)的**冷启动信号源**:新用户没有任何点击和收藏行为,能拿到的唯一偏好输入就是他自己勾选的兴趣。

因此 F5 的产出不止是一张表,而是**一套能被下游消费的偏好表示**。

## 2. 目标

| 编号 | 目标 | 达成情况 |
| ---- | ---- | ---- |
| G1 | 提供一份受控的学科标签词表 | 33 个标签,6 个分类 |
| G2 | 用户可多选,并给每个标签标 1–5 的权重 | ✅ |
| G3 | 偏好能被 REQ-002/REQ-004 直接消费 | 每个标签携带 S2 过滤值与检索词 |
| G4 | 接口幂等、语义简单,前端不必推理状态 | PUT 全量替换 |
| G5 | 有自动化回归覆盖 | 15 条集成测试 |

**非目标**(明确不做,避免范围蔓延):

- 不做标签的增删改管理后台 —— 词表随代码版本走
- 不做标签的自动推荐("你可能还喜欢")—— 属于 REQ-004
- 不做用户自定义标签 —— 见 3.1

## 3. 系统设计

### 3.1 为什么是受控词表,而不是自由输入

标签最终要喂给检索(REQ-002)和推荐(REQ-004)。若允许自由输入,「机器学习 / ML /
machine learning」会变成三个互不相干的字符串:用户兴趣向量无法对齐,也没法拿它去查论文。

自由输入要么配一套同义词归一(成本高、效果不稳定),要么在下游做模糊匹配(引入不可控噪声)。
受控词表把这件事一次性解决在入口。

**代价**:用户必须能在词表里找到自己。这靠"分类 + 足够细的粒度"来缓解 —— 见下条。

### 3.2 为什么不直接用 Semantic Scholar 的 fieldsOfStudy

S2 的 `fieldsOfStudy` 是一个**只有 23 个大类**的受控词表,「Computer Science」是其中**一个**值。

PaperPulse 面向的是 CS 方向的科研场景,绝大多数用户的兴趣都落在 Computer Science 里。
如果用户能选的只有这一项,推荐模块从兴趣标签里学到的信息量是 **0 bit** —— 选了等于没选。

所以本项目的标签是**细粒度研究领域**(推荐系统 / 序列推荐 / 冷启动推荐 / 图神经网络 …),
同时**每个标签额外携带**它对应的 S2 过滤值 `s2Field` 与检索词 `s2Query`:

```java
RECOMMENDER_SYSTEM("推荐系统", "信息检索与推荐", "Computer Science", "recommender system"),
```

这样既保留了细粒度信号,又能在调用 S2 时正确降级到大类过滤。
**细粒度用于建模,粗粒度用于检索** —— 两者不是二选一。

### 3.3 词表定义在代码里,不进数据库

| 方案 | 取舍 |
| ---- | ---- |
| **枚举(采用)** | 随代码版本走、可评审、可 diff、编译期就发现重复 key |
| 数据库表 | 改词表要写迁移脚本;但可以做成运营后台 |
| 配置文件 | 介于两者之间,但失去类型安全 |

词表是**受控**的,意味着它的变更应该经过代码评审,而不是某天有人在后台点了两下。
当前阶段没有运营角色,枚举是成本最低且最不容易出错的形态。

用户表里存的是枚举的 `key()`(小写枚举名),**不存展示名** —— 这样以后改中文展示名不影响已有数据。

### 3.4 标签的分类与分布

| 分类 | 数量 | 标签 |
| ---- | ---- | ---- |
| 人工智能 | 9 | 机器学习 / 深度学习 / 大语言模型 / 自然语言处理 / 计算机视觉 / 强化学习 / 生成模型 / 知识图谱 / 多模态学习 |
| 信息检索与推荐 | 7 | 推荐系统 / 信息检索 / 检索增强生成 / 图神经网络 / 序列推荐 / 冷启动推荐 / 文本表示与向量检索 |
| 可信与可解释 | 5 | 可解释人工智能 / 因果推断 / 公平性与偏见 / 不确定性建模 / 人工智能安全 |
| 数据与系统 | 6 | 数据库系统 / 分布式系统 / 软件工程 / 信息安全 / 人机交互 / 程序语言 |
| 数学基础 | 2 | 最优化 / 概率与统计 |
| 交叉学科 | 5 | 生物信息学 / 医学人工智能 / 机器人学 / 计算社会科学 / 教育技术 |

"信息检索与推荐"与"可信与可解释"两组被刻意加厚:它们既是本项目的技术方向,也是最可能被
使用者勾选的区域。

### 3.5 权重为什么是 1–5,而不是 0–1 的小数

- **整数**符合"打星"的直觉,前端可以直接渲染成五颗星,不需要解释"0.7 是什么意思"
- **1–5** 而不是 **0–4**:0 分意味着"不感兴趣",而"不感兴趣"的正确表达方式是不勾选它
  —— 让 0 成为合法值会制造两种语义相同的表示
- 小数精度带来的区分度是**虚假的**:用户不可能稳定地分辨 0.7 和 0.75

### 3.6 一个用户最多 10 个标签

限制不是怕存不下,而是怕**失去区分度**:标签选得越多,每个标签能贡献的信号越弱,最后等于没填。

这个上限同时被两层拦住:

- **Bean Validation**(`@Size(max = 10)`)—— 结构层的快速失败
- **常量 `InterestService.MAX_TAGS`** —— 接口把上限通过 `GET /api/interests` 返回给前端,
  前端据此渲染,而不是硬编码一个 10

## 5. 数据流

### 写路径(全量替换)

```
PUT /api/users/me/interests
   │  { "interests": [ {"tag":"nlp","weight":5}, ... ] }
   ▼
JwtAuthenticationFilter ──► SecurityContext(userId)
   ▼
InterestController  (@Valid 校验: 非空 tag、weight ∈ [1,5]、最多 10 条)
   ▼
InterestService.replaceFor(userId, items)
   ├─ ① 逐条查词表 + 查重  ──── 任一失败 → 400,**此时还没动过数据库**
   ├─ ② deleteAllByUserId(userId)   JPQL 批量删除,当场执行
   └─ ③ saveAll(新实体)
   ▼
返回替换后的完整列表(200,不是 204)
```

**①②③ 在同一个 `@Transactional` 里**,中途失败整体回滚,不会出现"旧的删了、新的没进去"。

### 读路径

```
GET /api/users/me/interests
   ▼
findByUserId ──► 逐条查词表补 displayName / category ──► 过滤查不到的 key ──► 按词表顺序排序
```

## 6. 核心流程与关键决策

### 6.1 为什么是"全量替换"而不是增删改三条接口

标签最多 10 个,全量重写的开销可以忽略;换来的是**语义极其简单** —— 请求体就是最终状态。

如果拆成 POST(加一个)/ DELETE(删一个)/ PATCH(改权重),客户端就要自己维护"本地和服务端
是否一致":网络重试会重复添加、并发编辑会互相覆盖、断线重连后要重新同步。
这些问题在"提交最终状态"模型下**根本不存在**。

PUT 天然幂等:同一份请求体提交两次,结果一样。

### 6.2 校验必须先于删数据(F5-11)

`replaceFor` 里,词表校验和查重都在 `deleteAllByUserId` **之前**完成。

否则一次手滑(比如把 `nlp` 拼成 `no_such_tag`)会让请求在删完旧数据之后才失败 —— 事务虽然会
回滚,但**错误响应本身应该保证"什么都没发生"**,而不是依赖回滚来兜底。回滚是最后一道防线,
不是第一道。

### 6.3 为什么用 JPQL 批量删除,而不是派生的 `deleteByUserId`

**这是本项目最容易踩、也最不直观的一个坑。**

派生删除走的是"查出实体 → 逐个标记删除",而 Hibernate 刷盘时 **INSERT 先于 DELETE 执行**。
于是"标签没变、只是权重变了"这种最常见的场景会先插新行、再删旧行,撞上
`(user_id, tag_key)` 唯一约束直接报错:

```
Duplicate entry '3-recommender_system' for key 'user_interest.uk_user_interest_user_tag'
```

JPQL 的 `@Modifying` 批量删除是**当场执行**的,不存在这个次序问题。

**这不是推理,是实测过的。** 把实现换成派生版本后,F5-5 / F5-6 / F5-7 三条用例当场失败,
错误信息就是上面那一行。证据写在 `UserInterestRepository#deleteAllByUserId` 的注释里。

> 顺带说明:这个坑也反过来证明了那三条用例是**有意义的** —— 如果只测"新增标签"和"清空",
> 派生版本能通过全部用例,问题会一直潜伏到某天有人改了权重。

### 6.4 未知标签返回 400,而不是静默忽略(F5-11)

静默忽略会让用户以为保存成功了,实际却少存了几个 —— 这是**静默的数据丢失**。
在写接口上,明确的失败永远优于善意的猜测。

### 6.5 读的时候过滤掉词表里已下线的 key

标签被下线后,库里会残留旧的 key。读取时按词表过滤掉,让它们**静默消失**。

这看起来和 6.4 矛盾,其实方向相反:6.4 是**写入**时的用户输入错误,必须报错;
这里是**历史数据**的兼容问题,报错只会让用户看到一个他无法修复的报错,而且前端根本不认识这个标签。

### 6.6 `UserInterest` 用 `Long userId` 字段,不用 `@ManyToOne`

- 兴趣的任何操作都**不需要 `User` 实体**:拿到的 userId 来自已验证的 token
- 当前没有删除用户的功能,不存在"级联清理"的需求
- 避免 Hibernate 在多对一关联上生成代理对象、以及由此引入的 N+1 风险

将来真做了用户注销,再补外键与级联也不迟 —— 那时才知道级联的确切语义。

### 6.7 `PUT` 返回替换后的列表,而不是 204

前端提交完通常要立刻重绘。而且服务端会对内容做规整(排序、过滤已下线的标签),
**返回真实结果比让前端自己猜更可靠**。

### 6.8 DTO 里的 `weight` 用 `Integer` 而不是 `int`

用 `int` 的话,请求体里缺 `weight` 字段会被反序列化成 `0`,再被 `@Min(1)` 拦下报一句
"weight 必须大于等于 1" —— 用户明明没填,却被告知填错了数字。

用 `Integer` + `@NotNull`,缺字段时给出的是"weight 不能为空",**报错信息对得上真实原因**。

## 7. 接口

| 方法 | 路径 | 说明 | 鉴权 |
| ---- | ---- | ---- | ---- |
| GET | `/api/interests` | 词表,按分组返回,含 `minWeight` / `maxWeight` / `maxTags` | 是 |
| GET | `/api/users/me/interests` | 当前用户的标签 + 权重 | 是 |
| PUT | `/api/users/me/interests` | **全量替换**(含清空),返回替换后的列表 | 是 |

### 数据表

```sql
CREATE TABLE user_interest (
    id       BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id  BIGINT       NOT NULL,
    tag_key  VARCHAR(64)  NOT NULL,
    weight   INT          NOT NULL,
    CONSTRAINT uk_user_interest_user_tag UNIQUE (user_id, tag_key)
);
```

唯一约束是**业务不变量的最后一道防线** —— 服务层的查重负责给出友好的 400,
数据库的约束负责保证"即使服务层有 bug,也不可能存进两条重复标签"。

## 8. 技术选型原因汇总

| 决策 | 选择 | 主要理由 |
| ---- | ---- | ---- |
| 词表形态 | 受控枚举 | 变更需评审;避免同义词发散;编译期类型安全 |
| 标签粒度 | 细分领域 + 携带 S2 映射 | 大类在 CS 场景下信息量为 0;细粒度用于建模、粗粒度用于检索 |
| 存储内容 | 只存 key | 展示名可随时调整而不动数据 |
| 权重 | 整数 1–5 | 前端可直接渲染成星级;避免虚假精度 |
| 写入语义 | PUT 全量替换 | 幂等;客户端无需维护增量状态 |
| 删除方式 | JPQL 批量删除 | 规避 Hibernate"先插后删"撞唯一约束 |
| 关联方式 | 裸 `Long userId` | 不需要 User 实体;避免代理对象与 N+1 |

## 9. 测试

15 条集成测试(`InterestApiIntegrationTest`),覆盖三类容易出问题的地方:

| 分组 | 用例 | 针对的风险 |
| ---- | ---- | ---- |
| 词表 | F5-1 / F5-2 | 词表完整性、未登录 401 |
| 替换语义 | F5-3 ~ F5-8 | 少传的标签要真的消失、空数组要真的清空 |
| **写入次序** | **F5-6 / F5-7** | **改权重时标签没变,先插后删会撞唯一约束** |
| 校验 | F5-9 ~ F5-13 | 权重越界、缺 weight、未知标签、重复标签、超上限 |
| 边界 | F5-14 | **恰好** 10 个必须被允许 |
| 隔离 | F5-15 | 用户之间互不影响 |

F5-14 存在的意义:边界用例写错方向的代价是双向的 —— 上限写成 `>=` 会连合法的第 10 个一起挡掉。
