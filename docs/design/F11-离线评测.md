# F11 离线评测

REQ-006 的阶段 1:把"尺子"造出来。

## 1. 背景

到这一步,项目已经有了一条完整的推荐链路(F10),但**没有任何办法回答"它到底行不行"**。
只能凭感觉说"推得一般",不知道有多一般,也不知道往哪个方向调。

离线评测要解决的就是这件事。它比它看起来难的地方在于:**推荐系统的评测需要标准答案**,
而我们没有。生产库里只有 3 个真实用户、几乎没有交互;论文是自己搜进来的,没有相关性标注。
**这个前提不解决,后面所有指标都是假的。**

## 2. 目标

阶段 1 交付:`docs/design/` 之外的**评测基础设施**。

1. **能从公开数据构造出一个带标准答案的评测集**
2. **指标实现正确**(Recall@K / NDCG@K),并用构造的小例子验证
3. **两个"必须打败"的对照**:随机、热门
4. **把当前的推荐算法接进去**,得到它在同一把尺子下的数字
5. 结果落成一份实验记录(`experiments/`)

**不在本次范围**:embedding 基线、SASRec、LLM 生成式推荐 —— 那是阶段 2/3/4。

**为什么阶段 1 单独拿出来**:如果尺子本身不可靠(指标算错、评测集有偏),上面接再多方法都是白搭。
先用两个"应该被打败"的对照校准它 —— **如果我们的算法连随机都打不过,那说明评测或算法至少有一个是坏的**,
这时候继续加方法毫无意义。

## 3. 系统设计

### 3.1 评测集:用引用关系当代理信号

学界常用做法(技术选型文档里也提过)。

```
用户   = 一篇论文(或一位作者)
交互   = 它引用过的论文        ← OpenAlex 的 referenced_works
切分   = 按年份:较早的引用 = 历史,较晚的 = 测试集
兴趣   = 从"历史引用"的主题推出来
候选池 = 该论文的全部引用 + 采样的负例
任务   = 把"测试集里的引用"排在候选池靠前的位置
```

**为什么用"论文"而不是"作者"当用户**:一篇论文的参考文献是一次完整的、时间上收敛的引用行为,
切分干净;而一位作者的引用分散在多年、多个主题上,噪声大得多。技术选型文档提的是"作者"版本,
这里收窄到"论文"版本 —— **更小、更干净的第一步**,作者的版本将来可以在同一套基础设施上扩展。

### 3.2 候选池为什么要加负例

只用"该论文的全部引用"当候选池的话,池子只有二三十篇,而且**全部都是相关的** ——
随便排都容易排中,指标会虚高到没有区分度。

所以加上从**全局论文池**里采样的负例(默认 100 篇)。

### 3.3 指标

| 指标 | 含义 |
| ---- | ---- |
| **Recall@K** | 测试集里的论文,有多少进了 top-K |
| **NDCG@K** | 排得越靠前越好,而不只是"进没进 top-K" |

两个都要:**只报 Recall 会掩盖"全挤在第 10 位"**,只报 NDCG 又不直观。

### 3.4 对比方法(阶段 1 只做前三个)

| 方法 | 作用 |
| ---- | ---- |
| **随机** | 下界。任何算法打不过它,说明实现有 bug |
| **热门**(被引数最高) | 经典强基线。**推荐系统打不过它就该反思** |
| **我们的算法** | 当前生产实现(见 3.5 的适配说明) |
| ~~BGE embedding~~ | 阶段 2 |
| ~~SASRec(RecBole)~~ | 阶段 3 |
| ~~LLM 生成式~~ | 阶段 4 |

### 3.5 我们的算法怎么接进来(一处重要的适配)

生产推荐器的工作方式是"**按兴趣标签去外部检索取候选,再打分排序**"。
而离线评测是在**固定候选池**上排序 —— 没有"检索"这一步。

所以接进来的是它**打分函数的移植版**:

```
分数 = 兴趣匹配 × 2 + 新近度(0~4)
```

- **兴趣匹配**:候选与"从历史引用推出的兴趣标签"的匹配度。
  生产环境里这个信息来自"哪个标签的检索捞到了它";固定池里没有检索,改为按候选的主题/标题与标签关键词比对
- **新近度**:与生产完全一致

**这是移植版,不是线上那条链路** —— 线上还多一步"按标签检索取候选",那一步不在本次评测范围内。
报告里必须写明这条边界,否则"我们的算法得分"会被误读成整条线的得分。

## 4. 模块划分

放在 ai-service 下 —— 它是**离线批处理**,不是服务接口;而且阶段 2/3 要用的 embedding 与 RecBole 都在 Python 侧。

```
ai-service/app/eval/
  datasets.py    从 OpenAlex 构造评测集(取种子 → 取引用 → 批量补年份与主题 → 切分 → 采样负例)
  metrics.py     Recall@K / NDCG@K(纯函数,可单测)
  methods.py     三个方法:随机、热门、我们的算法(打分函数移植)
  runner.py      跑一遍、汇总、输出表格
ai-service/scripts/run_evaluation.py   命令行入口
```

```
ai-service/tests/test_eval_metrics.py  指标的单测(用手算得出的例子)
ai-service/tests/test_eval_methods.py  三个方法的单测(不联网)
```

## 5. 数据流

```
run_evaluation.py
   ↓
datasets.build()
   ① 按领域检索一批种子论文(OpenAlex,带 referenced_works)
   ② 批量补全被引用论文的年份与主题(每批 50 个,减少请求数)
   ③ 每篇种子:按年份把引用切成 历史 / 测试
   ④ 采样负例,拼成候选池
   ↓
对每个"用户"(种子论文):
   ① 从历史引用推兴趣标签
   ② 三个方法各排一次序
   ③ 算 Recall@K / NDCG@K
   ↓
汇总成表格 → 打印 + 写入 experiments/
```

**缓存**:构造评测集要发不少请求(OpenAlex 每次约 2~3 秒)。抓到的原始数据落一份本机缓存,
重跑时不重复抓 —— 否则每调一次指标都要等好几分钟。

## 6. 核心流程

| 步骤 | 规则 |
| ---- | ---- |
| 太长/太短的引用列表怎么办 | 丢弃(少于 8 条切不出有意义的训练/测试) |
| 年份缺失的引用 | 丢弃 —— 时间切分必须有年份 |
| 历史为空 | 丢弃该用户 |
| 测试集为空 | 丢弃该用户 |
| 负例怎么采 | 从全局池里随机采,**与测试集不重合**;固定随机种子保证可复现 |
| K 取多少 | 5 与 10 各报一次 |

## 7. 技术选型原因

### 为什么用 OpenAlex 而不是 Semantic Scholar

- **现在可达**(实测 200),而 S2 匿名池一直 429
- **引用与作者数据齐全**,正是这一步需要的
- 免费、无需申请 key
- 顺带:接它同时能提高检索质量,一件事两用

### 为什么指标要单独写单测

指标算错是**静默的** —— 数字照样输出,只是无意义。
所以用手算得出的例子(比如"3 个测试项排在第 1、3、10 位")把公式钉死,
而不是"跑通了看起来差不多"。

### 为什么阶段 1 不碰 embedding / RecBole

先证明尺子能区分好坏。用"随机"和"热门"两个已知强度的对照来校准:
**如果热门排在随机前面、我们的算法排在随机前面,尺子就是活的**;
如果三个方法分数差不多,那多半是评测本身有问题,这时再上 embedding 只是浪费。

## 8. 未来扩展

| 方向 | 说明 |
| ---- | ---- |
| **阶段 2:BGE embedding 基线** | 用户兴趣向量 = 历史论文向量加权平均,cosine Top-K |
| **阶段 3:SASRec(RecBole)** | 序列推荐,标准的强基线 |
| **阶段 4:LLM 生成式推荐** | 与 F10 的确定性打分对比;到这一步 REQ-006 的原文才算做全 |
| **行为反馈闭环(R4)** | 有了评测才能改打分公式 —— **这是它排在评测之后的原因** |
| **作者的版本** | 把"用户 = 论文"扩到"用户 = 作者",更接近真实用户,但噪声更大 |

## 9. 必须写进报告的局限

1. **代理信号不等于真实偏好。** 作者引用某篇论文,不等于他"喜欢"它。
   这是学界公认的近似,但结论只能说"在这个代理下"
2. **主题映射是近似的。** 从候选的主题推兴趣标签要跨一层映射,会有损耗
3. **样本量受接口限流约束。** 能构造的"用户"数量有限,结论的统计显著性有限
4. **不可外推。** 在引用代理上表现好,不等于真实用户用着好

**这四条不是免责声明,是结论的一部分** —— 少了它们,那张对比表会被读成它不支持的结论。
