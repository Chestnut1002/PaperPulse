# F10 个性化推荐

REQ-004 的后端。按用户的兴趣标签推荐论文,每条附推荐理由。

## 1. 背景

到这一步为止,项目已经有了三块拼图:

- **REQ-001** 给了用户、兴趣标签(1–5 权重)、收藏 / 阅读历史 / 评分三组行为数据
- **REQ-002** 给了从三个数据源取论文的能力(含跨源去重)
- 而 **F5 设计兴趣标签时,每个标签就带了 `s2Query`**(如「推荐系统」→ `"recommender system"`),
  当时写明的用途正是"供 REQ-002 检索与 REQ-004 推荐直接消费"

所以这一步是把已有的东西接起来:用户不必自己想检索词,系统按他的兴趣替他找。

## 2. 目标

1. 按兴趣标签给出个性化推荐,**每条说明为什么推荐它**
2. **排除用户已经打过交道的论文** —— 推荐的意义是"给你没看过的"
3. 有**探索位**,避免越推越窄(过滤气泡)
4. 建立一条**可复现、可评测的基线** —— 为 REQ-006 的离线评测、以及将来的 LLM 生成式推荐做对照

**不在本次范围**:前端页面(R3)、LLM 生成式推荐、离线评测指标。

## 3. 系统设计

### 3.1 候选从检索来,不是从库里挑

库里的论文是**用户自己搜过的**,拿它推荐等于把用户已知的东西再推一遍;而且语料规模取决于用户搜过多少,太小。

所以每次推荐都按兴趣标签的检索词去外部拉**新的候选**。

### 3.2 打分

```
分数 = 命中兴趣的最高权重 × 2  +  新近度(0~4)
```

| 项 | 取值 | 说明 |
| ---- | ---- | ---- |
| 兴趣匹配 | 1~5 的标签权重 × **2** | 取"命中的若干标签里权重最高的那个" |
| 新近度 | 0~4 | 当年 4 分,每老一年扣 1,超过 4 年不再扣(即 0 分) |

**兴趣的系数刻意更大** —— 论文推荐里"对不对口"比"新不新"更重要。

### 3.3 新近度的两个边界

- **年份未知时给 0 分,而不是倒扣。** 缺年份是"这条记录没写",不是"这篇很旧"。
  Crossref 确实不总给年份,倒扣会**系统性地压低它的候选** —— 那是对数据质量的偏见,不是对论文的判断。
- **超过四年不再继续扣。** 继续扣会让十年前的论文分数无下限地低,而它们的兴趣匹配分是一样的;
  扣到 0 已经表达了"不够新",再扣只是放大同一个信号。

### 3.4 探索位(`diversity_ratio`,默认 0.3)

预留 `round(limit × ratio)` 个名额给**没命中主要兴趣**的候选。不这么做的话,
用户只看得到自己最强的那个方向,越推越窄。

**两条边界规则:**

- **两边各留至少一个位置**(`0 ≤ 探索位 ≤ limit - 1`):否则参数取 0 或 1 时会退化成
  "全是主方向"或"探索位把主方向挤光"
- **哪边候选不够就用另一边补满** —— 宁可少一点探索,也不要返回不满一页

### 3.5 主要兴趣的判定

"主要兴趣"取**命中次数最多的那个标签**,而不是"分数最高那篇命中的标签"。
后者的基准会随单篇论文的排序变动而抖动,前者稳定得多。

## 4. 模块划分

```
ai-service/
  app/sources.py      find_candidates()   多路并发取候选 + 按论文合并
  app/schemas.py      Candidate{Query,Request,Paper,Response}
  app/main.py         POST /recommend/candidates

backend/.../recommend/
  RecommendationController   GET /api/users/me/recommendations
  RecommendationService      取候选 → 排除 → 打分 → 探索位 → 理由
  AiRecommendClient          调 ai-service(与检索共用 RestClient)
  dto/AiCandidateResponse    外部契约
  dto/RecommendationResponse 对外响应

backend/.../library/LibraryService.knownPaperIds   收藏 ∪ 读过 ∪ 评过分的并集
backend/.../config/AiServiceConfig                 ai-service 的 RestClient(超时只配一处)
```

**为什么取候选放在 Python 侧**:它本质是"多路检索",而检索的能力(三源并发、跨源合并、限流重试)
已经在那里了。放 Java 侧等于把那套逻辑再写一遍。

**为什么打分放在 Java 侧**:它要用到用户的兴趣权重与行为数据,而那些都在 Java 侧。

## 5. 数据流

```
GET /api/users/me/recommendations
   ↓
① 回查用户(token 签名有效 ≠ 用户还在,与其余接口同一个落点)
② 读兴趣标签;为空 → 直接返回引导文案,**不去麻烦上游**
③ 取权重最高的 4 个标签,各自的 s2Query 作为检索词
   ↓  POST /recommend/candidates {queries:[{tag,keywords}], perQuery:8}
   ↓  Python:4 路并发 × 每路 3 个源 → 按 DOI / (来源,外部ID) 合并 → 累积 matchedTags
④ 候选落库(走既有的 resolve,跨源合并自动生效)
⑤ 排除 knownPaperIds(收藏 ∪ 读过 ∪ 评过分)
⑥ 打分 → 降序
⑦ 排探索位 → **再按分数排一次**
⑧ 构造理由 → 返回
```

## 6. 核心流程

### 一次推荐的判定顺序

| 步骤 | 规则 |
| ---- | ---- |
| 有候选吗 | 上游每一路都失败 → 503;有路成功但没结果 → 正常返回空列表 |
| 要它吗 | 已收藏 / 读过 / 评过分的排除 |
| 排多前 | `兴趣权重 × 2 + 新近度` |
| 谁进榜 | 主方向取 `limit - 探索位`,探索位取其余;**选完仍按分数排** |
| 为什么 | 「命中你的兴趣『推荐系统』(权重 5)· 2024 年」 |

## 7. 技术选型原因

### 为什么这一版不用大模型

1. 兴趣标签自带检索词,**没有需要拆解的自然语言** —— 检索那一步用 LLM 是因为用户输入是一句话,这里不是
2. 打分必须**可解释、可复现、可测试** —— 一个纯函数能被单测钉死,一次 LLM 调用不能
3. **它是基线。** 将来做"LLM 生成式推荐"时,没有基线就无法回答"到底有没有变好"。
   技术选型文档里本来就规划了"基线 vs 进阶"两层

### 为什么取权重最高的 4 个标签

不设上限的话,十个标签就是十组检索(每组三个源)—— 又慢又招外部接口烦。
四个够覆盖"主要方向 + 一点探索"了。

### 为什么探索位不决定顺序

实测发现列表看起来根本没排序:

```
 3. [10.0] 2013 年的论文   ← 主方向
 7. [12.0] 2026 年的论文   ← 次要方向,分数更高却排在后面
```

原因是探索位被**追加在末尾**。这暴露出对它的理解偏了:
**它应该决定"谁能进榜",而不是"排在第几"**。
选完之后仍按分数排 —— 探索位的候选本来就因为兴趣权重低而分数偏低,
排序后自然落到后半段,该被看到的仍然看得到。

### 为什么候选全部落库(而不是只存展示的那几篇)

一次推荐取约 25 篇候选、只展示 8 篇,但**全部都会落库**。

好处是语料在长大,而 REQ-006 的离线评测正需要一个可以反复查的论文池。
代价是 `paper` 表里会有"推荐捞出来但没人看过"的论文 ——
**分析时不能把"库里的论文"等同于"用户看过的"**。

要收紧得先有一个按身份(而非本地 id)比对"用户已知论文"的办法,那是另一件事。

## 8. 未来扩展

| 方向 | 说明 |
| ---- | ---- |
| **R3 前端「今日推荐」页** | 设为首页;理由字段已经在接口里,直接展示即可 |
| **REQ-005 丰富的推荐理由** | 现在是最简版(命中哪个兴趣、权重多少)。更丰富的理由(如"因为你在读 X 方向")交给 LLM |
| **REQ-006 离线评测** | 有了这条基线,可以量 Recall@K / NDCG@K,并让"进阶版"与它对比 |
| **进阶:LLM 生成式推荐** | 把用户历史论文序列喂给 LLM,让它从候选池里生成推荐。对比基线才有意义 |
| **候选缓存** | 每次打开推荐页都跑 4 组检索。若成为瓶颈,与之前讨论过的搜索缓存是同一件事 |
| **推荐质量** | 当前**推得一般**是有意接受的:标签检索词本身宽泛,打分只能排序、不能把不相关的变相关。目标先是"链路通、可评测" |

**已知的评测风险**:`diversityRatio` 会改变展示哪些论文,所以离线评测时**必须固定它**并写进实验记录,
否则两次实验的数字不可比。
