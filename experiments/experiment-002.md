# experiment-002:推荐算法的离线评测(阶段 1)

**日期**:2026-09-30
**对应功能**:REQ-006 阶段 1 —— 评测基础设施 + 三个方法的对比
**设计文档**:`docs/design/F11-离线评测.md`

---

## 要回答的问题

到这一步项目已经有了一条完整的推荐链路,但**没有任何办法回答"它到底行不行"** ——
只能凭感觉说"推得一般"。这次要把尺子造出来并校准。

## 模型 / 方法

阶段 1 只做三个方法(embedding / SASRec / LLM 是后续阶段):

| 方法 | 说明 |
| ---- | ---- |
| **随机** | 下界。任何算法打不过它说明实现有 bug |
| **热门** | 按被引数排序。经典强基线 |
| **我们的算法** | 当前生产实现的**打分函数移植版**(`兴趣匹配 × 2 + 新近度`) |

## 数据集

**构造方式**:用学术引用关系当代理信号(学界常用做法)。
一个"用户"是**一篇论文**,不是一位作者 —— 一篇论文的参考文献是一次完整的、时间上收敛的引用行为,
比作者多年跨主题的引用干净得多。

```
种子论文(OpenAlex,计算机领域 field 17,2019–2023,有引用数据)
   ↓ 取它的 referenced_works
被引用论文(批量补全年份与主题)
   ↓ 按年份排序后 70% / 30% 切分
历史(5~338 篇)  +  测试集(3~146 篇)
   ↓ 从历史论文的主题里数出最常出现的 5 个当兴趣关键词(权重 5~1)
候选池 = 测试集 + 采样的负例(排除该用户自己的引用)
```

**为什么候选池里不放历史项**:放进去的话模型会把它们排到前面,白占位置却不计分。

## 参数

| 参数 | 取值 | 说明 |
| ---- | ---- | ---- |
| `seed_count` | 40 | 取多少篇种子论文当"用户";实际构造出 **39** 个有效用例 |
| `min_references` | 8 | 参考文献太少的切不出训练/测试 |
| `negatives_per_user` | **300** | 见下方「问题一」,从 100 提到 300 |
| `max_keywords` | 5 | 从历史里推几个兴趣关键词 |
| `history_ratio` | 0.7 | 较早的多大比例算历史 |
| `seed` | 42 | **固定** —— 否则每次跑出的数字都不一样,没法比较 |
| K | 5、10 | 两个都报 |
| 数据源 | OpenAlex | 现在可达、引用数据齐全、免费无需 key |
| 领域 | Computer Science(field 17) | 项目关心的是 CS/ML,拿核物理论文评测离项目太远 |

**候选池**:中位 324 篇;相关项占比平均 **9.3%**。

## 结果

```
评测用户数:39

方法            recall@5   recall@10      ndcg@5     ndcg@10
----------------------------------------------------------
随机              0.0119      0.0287      0.0584      0.0845
热门              0.0189      0.0302      0.0860      0.0868
我们的算法           0.1878      0.3249      0.6439      0.6737
```

**阶梯成立:随机 < 热门 ≪ 我们的算法。** 我们的算法在 recall@10 上是随机的 **11 倍**、
在 ndcg@10 上是 **8 倍**。尺子是活的。

## 问题

### 问题一:负例只有 100 时任务太饱和

第一版 `negatives_per_user = 100`,结果是这样:

```
方法            recall@5   recall@10      ndcg@5     ndcg@10
随机              0.0466      0.0867      0.2447      0.2447
热门              0.0494      0.0845      0.2479      0.2162
我们的算法           0.2261      0.3832      0.7691      0.7835
```

**相关项占比 21.9%** —— 中位数 24 个测试项对 100 个负例。常见做法在个位数百分比,
22% 意味着"瞎排也能中五分之一",指标被压缩、区分度下降。

提到 300 后占比降到 **9.3%**,而且**热门从"和随机差不多"变成"略强于随机"**,
对比阶梯才真正显出来。

> 顺带解释一个看着像 bug 的现象:相关项占比固定时,**随机排序的 NDCG@K 期望就等于这个占比**,
> 与 K 无关 —— 所以 100 负例那一版里 `ndcg@5 = ndcg@10 = 0.2447` 是数学上必然的,不是算错了。

### 问题二(设计取舍,不是 bug):负例取自引用邻域

负例是从**所有种子论文引用过的论文**里采的,不是从"全网随机论文"里采。

结果是:候选池里全是被引用过的、同时期的同类论文 —— **流行度不区分它们**,
所以"热门"这个基线在这个任务上几乎不奏效(只比随机好一点)。

**这是有意保留的**:它让任务变成"从同一领域的被引论文里挑出真正相关的",
比"从随机论文里挑"难得多,也更有意义。热门基线弱不代表它有问题,是这个任务不吃这一套。

### 问题三:兴趣关键词与线上不是同一套词表

评测里直接用 **OpenAlex 的主题词表**当兴趣关键词,没有映射到我们的 34 标签词表 ——
少一层有损映射。形式的(K 个关键词 + 1~5 权重)与生产一致,词表不同。

### 问题四:一个不是 bug 但要注意的点

`热门` 的 `ndcg@5 = 0.0860` 与 `ndcg@10 = 0.0868` 几乎一样 —— 因为它把所有论文按被引数
排成一个固定顺序,与用户无关;加长列表只是多填几个位置。

## 局限(必须和结论一起看)

1. **引用关系是代理信号,不等于真实偏好。** 作者引用某篇论文不等于他"喜欢"它。
   结论只能说"在这个代理下"
2. **评的是排序,不是整条链路。** 线上还多一步"按兴趣标签检索取候选",固定候选池里没有它。
   所以这个分数**不能**读成"线上推荐的准确率"
3. **样本量小。** 39 个用例、一个领域、一个时间段,统计显著性有限
4. **不可外推。** 在引用代理上表现好,不等于真实用户用着好

## 下一步优化

1. **阶段 2:BGE embedding 基线** —— 用户兴趣向量 = 历史论文向量加权平均,cosine Top-K。
   到这一步才能回答"我们的关键词匹配 vs 语义向量,哪个更好"
2. **阶段 3:SASRec(RecBole)** —— 序列推荐,标准强基线
3. **阶段 4:LLM 生成式推荐** —— 与 F10 的确定性打分对比,REQ-006 的原文才算做全
4. **扩大样本**:换领域、换时间段各跑一遍,看结论稳不稳
5. **把结论用起来**:R4(行为反馈闭环)要改打分公式,**改之前必须先有这张表当基准** ——
   否则无法判断改动是变好还是变差
