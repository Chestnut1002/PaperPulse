## 要回答的问题

**"语义向量 vs 关键词匹配,到底哪个更好?"**

如果 embedding 明显赢,生产推荐器就值得换成向量;如果差不多甚至更差,
那现在这套关键词匹配就是合理的选择 —— 而且省下一大块依赖。

## 模型

| 项 | 取值 |
| ---- | ---- |
| 模型 | **`BAAI/bge-base-en-v1.5`**(768 维) |
| 备选 | `BAAI/bge-m3` —— 项目的既定选型,但**本机网络下它下不动**(见问题一) |
| 下载源 | `hf-mirror.com`(本机到不了 `huggingface.co`) |
| 输入文本 | **标题 + 主题短语**(不含摘要) |
| 用户向量 | 历史论文向量的**平均**(不加权),再归一化 |

## 数据集与参数

与 experiment-002 完全相同(同一份缓存、同一个随机种子),**唯一变量是方法**:

- 39 个"用户"(种子论文),候选池中位 324 篇,相关项占比 9.3%
- 数据源 OpenAlex,计算机领域,2019–2023

## 结果

```
方法            recall@5   recall@10      ndcg@5     ndcg@10
----------------------------------------------------------
随机              0.0119      0.0287      0.0584      0.0845
热门              0.0189      0.0302      0.0860      0.0868
我们的算法           0.1876      0.3247      0.6355      0.6685
BGE embedding      0.1666      0.3173      0.6470      0.6550
```

**两者几乎持平**,而且互有胜负:recall 上我们的略高(0.3247 vs 0.3173),
ndcg@5 上 embedding 略高(0.6470 vs 0.6355)。

### 但"看起来差不多"不是结论 —— 要看区间

```
我们的算法 减 BGE embedding 的 ndcg@10:
平均 +0.0135,95% 区间 [-0.0559, +0.0913] → 分不出高下(区间跨过 0)
```

用**配对自助法**(同一个用户面对同样的候选池,两者的差才是"方法之差";
直接把两组分数拿来比会被用户之间的差异淹没)。

**区间跨过 0:在 39 个用户上,两个方法分不出高下。**

## 结论

**没有证据表明 embedding 比现在的关键词匹配更好。**

两个方法都远超随机(约 11 倍 recall@10)和热门,但**彼此之间分不出高下**。

**对项目的直接影响**:把生产推荐器换成向量方案,要付出一个 440MB 模型 + torch 依赖的代价,
而在这次评测里**换不来可测量的收益**。所以**先不换**。

## 问题

### 问题一:原定的 BGE-M3 在本机网络下下不动

M3 约 2.2GB。实测 `hf-mirror.com` 的速率**从 44 MB/分掉到 9 MB/分**,2.2GB 要四个小时,
而且中途连接断过一次(文件从 1996MB 掉回 145MB 重下)。

换成 `bge-base-en-v1.5`(约 440MB)—— **61 秒下完并加载**,768 维,
是最常用的标准英文模型。评测语料本来就是英文标题,小模型的劣势在这里体现不出来。

**要换回 M3 就设 `EVAL_EMBEDDING_MODEL=BAAI/bge-m3`。** 换了模型数字会变,必须重跑。

### 问题二(真 bug,靠"重跑一次发现又联网了"才暴露):缓存从来没命中过

缓存键用了 Python 的内置 `hash()`:

```python
digest = str(abs(hash(tuple(sorted(ids)))))
```

**内置 `hash()` 对字符串每个进程都不同**(有随机盐)。所以每次跑都是新键 ——
**缓存永远命中不了,等于没有缓存**,每次都要重新联网抓几千条记录。

改成 `hashlib.sha1`。这类 bug 不会报错,只会让程序**每次都慢**,很容易被当成"本来就该这么慢"。

### 问题三:OpenAlex 会持续抖动

实测连续遇到 504(查询太宽)、500(内部错误),还有一次返回 200 但**响应里没有 `results` 字段**。

处理:退避重试 4 次;**重试仍失败就把批量拆成两半**再问(从 50 个拆到 25、12……)。
4xx 不重试 —— 那是请求本身写错了,重试没有意义。

### 问题四(方法本身的局限):embedding 基线被削了一刀

输入只有**标题 + 主题**,没有摘要 —— OpenAlex 的摘要是倒排索引格式,还原要额外一段代码。

**这让 embedding 基线偏弱**:线上是有摘要可用的。
所以结论只能说"**在这个输入下**分不出高下",不能说"embedding 一定不比关键词好"。

## 局限

1. 与 experiment-002 相同的四条(代理信号、只看排序、样本量、不可外推)
2. **embedding 少用了摘要**,基线偏弱
3. 39 个用户、一个领域、一个时间段 —— **"分不出高下"不等于"两者一样好"**,
   只说明**这个样本量下测不出差别**

## 下一步优化

1. **把摘要喂给 embedding 再跑一次** —— 这是最直接的"公平性补强"。如果加上摘要后 embedding 明显赢,
   结论就要改
2. 换 M3 再跑(网络恢复后)—— 模型更大,可能拉开差距
3. **阶段 3:SASRec(RecBole)** —— 序列推荐,标准强基线
4. **阶段 4:LLM 生成式推荐** —— REQ-006 的原文才算做全
5. 扩大样本:换领域、换时间段各跑一遍,看结论稳不稳
