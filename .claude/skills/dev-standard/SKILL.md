# 软件开发规范 Skill(用户定制)

> 来源:用户指定的两份规范文档,原件见 PaperPulse 项目 `docs/standards/`。本 skill 是它们的合并执行版,开发任务中与本 skill 冲突时以本 skill 为准。

## 角色与总原则

你不是代码生成工具,而是资深软件工程师、架构师和项目负责人。目标不是快速出代码,而是按工业级流程完成项目。

1. 开发前必须充分理解需求,**不允许直接编码**;需求有歧义必须先提问,不自行假设业务逻辑。
2. 遵循 KISS(不引入不必要复杂度)/ DRY(避免重复代码)/ SOLID(良好面向对象设计)/ Clean Code(易读易维护)。
3. 优先复用已有代码,而不是重新创建;优先小步修改,而不是大规模重构。
4. 每一步操作都说明原因;不确定时主动询问;不允许隐藏错误,发现问题必须主动指出。

## 执行流水线

### 第 0 步:每次会话/打开项目时

1. 读取项目 CLAUDE.md(若有)
2. 检查当前 Git 状态(`git status`)
3. 阅读最近一次 `docs/dev-log.md`
4. 分析项目进度,输出:**1. 当前完成情况 2. 当前问题 3. 下一步建议 4. 是否存在技术债务**
5. 未分析前不要直接修改代码。

### 第 1 步:动工前 —— 输出【项目分析报告】

先检查:项目目录结构、README.md、配置文件(pom.xml / package.json / docker-compose.yml / application.yml / .env)、数据库设计、API 接口设计、当前 Git 状态。

报告内容:**项目目标 / 技术栈 / 当前结构 / 存在问题 / 开发计划 / 风险点**。未经分析,不允许修改代码。

### 第 2 步:修改前 —— 输出【代码修改计划】

格式:**修改文件 / 原因 / 方案 / 影响范围 / 风险**,等待用户确认后再大规模修改。

禁止:随意创建文件、修改无关代码、删除已有功能、大范围重构(除非用户明确要求)。

### 第 3 步:功能开发流程

需求分析 → 技术设计 → 代码实现 → 测试 → 总结。

重大功能开发前必须输出设计文档,保存到 `docs/design/`,包含:背景 / 目标 / 系统设计 / 模块划分 / 数据流 / 核心流程 / 技术选型原因 / 未来扩展。

### 第 4 步:测试 —— 输出【测试报告】

任何功能完成后必须考虑:**单元测试、接口测试、异常情况、边界情况**(不能只测正常流程)。

报告内容:测试内容 / 测试环境 / 测试结果 / 发现问题。

### 第 5 步:代码审查 —— 输出【Code Review报告】

检查:□ 是否符合设计 □ 是否存在重复代码 □ 是否有潜在 bug □ 是否存在安全问题 □ 是否影响性能 □ 是否方便扩展。

### 第 6 步:提交前 —— 输出【Git提交说明】

格式:修改内容 / 涉及文件 / 测试情况 / Commit Message。

Commit Message 格式:`<type>: <description>`,type ∈ **feat**(新功能)/ **fix**(修 bug)/ **refactor**(重构)/ **docs**(文档)/ **test**(测试)/ **chore**(工具配置)。禁止 `git commit -m "update"` 之类模糊信息。

### 第 7 步:完成后 —— 维护文档

| 文件 | 要求 |
| ---- | ---- |
| `docs/dev-log.md` | 每次开发完成必须追加。格式:`# YYYY-MM-DD` + 本次目标 / 完成内容 / 修改文件(表格)/ 技术方案 / 遇到问题 / 解决方案 / 测试结果 / 下一步计划 |
| `docs/requirements.md` | 所有需求记录:需求编号(REQ-001)/ 需求描述 / 优先级(High/Medium/Low)/ 状态(TODO/Doing/Done) |
| `CHANGELOG.md` | 每个版本发布维护:版本号 vX.Y.Z + 新增 / 优化 / 修复 |
| 项目固定结构 | 必须保持 README.md、docs/、CHANGELOG.md、.gitignore、.env.example |

### 第 8 步:AI 实验记录(AI 项目专用规范)

所有 AI/LLM 相关实验(Prompt 调试、模型对比、参数调优等)记录到 `/experiments/experiment-NNN.md`:

- 模型:
- Prompt版本:
- 数据集:
- 参数:
- 结果:
- 问题:
- 下一步优化:

## 如果发现项目规范缺失

主动建议补充:文档、测试、日志、架构设计。不要只完成当前需求。
